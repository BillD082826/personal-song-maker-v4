# LyriBop Workflow Rules

Mandatory protocol — established October 24, 2026.

## Review before action

Before recommending a path, changing files, giving setup instructions, or asking Bill to act, review the goal, current evidence, existing workflow guidance, approved decisions, and relevant unresolved work. Explain what is already complete, what remains uncertain, and the intended result. Read-only inspection needed for that review may proceed. Do not restart completed work or treat chat memory as verification.

## Compare options before choosing

Compare the practical available options, including existing tools and doing nothing when appropriate. Consider reliability, user effort, cost, permissions, reversibility, and maintenance. Recommend the simplest option that reliably meets the goal and explain the choice briefly. Do not send Bill through a setup sequence before checking whether an easier supported route already exists.

## Use the simplest reliable automation

Use available tools to complete authorized work and verify the result. Prefer existing supported workflows over new infrastructure or a long manual sequence. Automate repeatable work where it reduces effort without adding fragility. Identify steps that actually require Bill's participation. Never imply an integration, token, deployment, or publication works merely because setup screens exist.

## Stop and reassess on repeated friction

Immediately stop the current approach when the same obstacle recurs, instructions cycle, or repeated attempts fail to produce new evidence. Do not keep asking Bill to repeat the same action. State the obstacle, review assumptions and actual screen/error evidence, compare alternatives again, and choose a simpler supported path or record the blocker. Retry only when new evidence supports a materially different attempt. Preserve the last verified checkpoint.

## One user action at a time

When Bill must participate, give one concrete action, its purpose, and the expected visible result. Wait for that result before giving the next action. Do not bundle navigation, permission changes, authentication, and publishing into a checklist for Bill. Continue independent authorized work where possible. Review-before-action is mandatory; it does not require repeatedly asking for approval already provided.

## Start every new chat

1. Read STORYSONG_PROJECT.md, including its top reference, then this protocol; inspect the relevant current status, Master TODO, latest dated checkpoints, and task-specific guidance before acting.
2. For repository work, inspect the current branch, working tree, and relevant recent history. Preserve existing unrelated changes.
3. Briefly state the current verified checkpoint, unresolved work, and the scope authorized in this chat. Resolve conflicts using dated evidence; do not silently replace historical records.
4. Resume only the requested task. A handoff, new chat, or change of mode does not authorize restarting account setup, authentication, publishing, deployment, or application changes.
5. If needed prior chat details are unavailable, label the gap and use verified files/screens. Do not invent missing confirmations.

## Keep the continuity record

STORYSONG_PROJECT.md remains the authoritative project ledger: history, decisions, dated verification, and unresolved work stay there. This file defines how work is performed. Preserve the ledger's history; add dated corrections/checkpoints instead of deleting old entries. Record significant outcomes promptly, distinguish observation from inference, and close tasks only on evidence. Follow existing checkpoint/backup/Git guidance within the authorized scope; do not commit unrelated files or claim a backup, push, deployment, or publication occurred without verification.
